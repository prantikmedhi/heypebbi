# Service API and streaming contract

Status: documentation only. [CONTRACT](../CONTRACT.md) owns product vocabulary; [openapi.json](openapi.json) is OpenAPI 3.1 / JSON Schema 2020-12 and owns every REST request/response field and every decoded streaming message. This document owns protocol sequencing, authorization and invariants that structural schema cannot express. No domain, tenant, service or Azure deployment is asserted to be provisioned.

## Shared wire rules

- All Pebbi JSON uses camelCase and `schemaVersion: 1`; identifiers are opaque, case-preserved UUID strings, UTC timestamps end in `Z`, and quantities are nonnegative integers within JSON's exact integer range. Vendor Stripe IDs are opaque provider strings; the signed incoming Stripe event is an explicit vendor-owned snake_case/version exception, not a new Pebbi schema style.
- `/healthz` alone is outside `/v1`. Paths below are literal; there are no hidden conversation, file, screenshot, task-cancel or cross-device-sync endpoints. Entra authorization/token endpoints and Stripe-hosted pages are external services, not additional Pebbi routes.
- `Content-Type: application/json` for REST request bodies; successful nonstreaming bodies are JSON. `DELETE /v1/devices/{deviceId}` returns 204 without a body. Unknown request properties, invalid enum values, malformed IDs, invalid UTF-8, duplicate JSON keys, nonfinite numbers and unsafe integers are rejected before dispatch.
- General request limit: 12 MiB; non-inference JSON limit: 64 KiB, except signed Stripe events capped at 1 MiB. `/v1/ai/responses` may include at most 8 MiB of decoded selected image content in total, no remote image URLs, no more than 128 messages, 32 content blocks per message and 64 tools. Text/definition limits also apply exactly as in the schema. Decode and inspect MIME rather than trusting a label.
- `X-Request-Id` is an optional UUID, server-generated if absent and echoed in responses. It is correlation, not authorization. No request ID, path or exception log may include content or secrets.
- `Cache-Control: no-store` on all API responses, including account data and tokens. HTTP errors are JSON until a stream has started. HTTPS is mandatory outside a developer-only loopback test. Do not redirect authenticated requests to another origin.
- `Authorization: Bearer <Entra access token>` is required except public health, signed Stripe webhook, internal metering and session-token WebSocket upgrades. No cookies are needed for native API calls. If server-rendered account pages use cookies, they require Secure/HttpOnly/SameSite cookies and CSRF protection; they do not weaken the API bearer contract.
- `X-Pebbi-Device-Id` **and** `X-Pebbi-Device-Token` are required together with the account bearer for every device-bound REST endpoint (all app-authorized endpoints except `GET /v1/me`, `POST /v1/devices/enrollments` and `POST /v1/devices`). The ID is public; verify the separate credential digest is bound to that exact account/device and nonrevoked enrollment. Reject duplicate credential/identity headers. Another owned device ID with a stolen bearer alone never authenticates. The finalizer and webhook use their own authentication and no device headers.
- Required `Idempotency-Key` values are UUIDs. Optional W3C `traceparent` may be validated for telemetry only, never propagated into identity/permission decisions. Reject sensitive bearer query parameters; never log authorization, device credentials, enrollment ID tokens/nonces, signature, cookies, session tokens or signed URLs. Disable automatic HTTP retries for nonce-returning enrollment creation and secret-returning registration/session minting.

## Authentication and identity

Microsoft Entra External ID is the identity authority, not a password database in Pebbi. Native sign-in uses AuthenticationServices/system browser, OIDC authorization code and PKCE `S256`; fresh cryptographic verifier, `state` and `nonce` per attempt, bounded expiry and exactly one callback consumption. Register an exact native redirect URI for bundle `com.heypebbi.app`; the actual URI/client/tenant/issuer/audience are deployment inputs, not guessed from `heypebbi.com`. No embedded web password UI and no native client secret.

The native client validates the ID token issuer/audience/signature/nonce/time and state/redirect match before associating an account. Generic API bearer authentication accepts access tokens, never ID tokens, and verifies signature using issuer-pinned discovery/JWKS, approved algorithms, configured issuer and API audience, lifetime (maximum 60-second skew), expected tenant/policy and the configured delegated API scope. Canonical account lookup uses pinned issuer/tenant plus the verified immutable signed `oid` and signed `tid` where provided, with an explicit verified tenant mapping when the issuer supplies tenant identity. Require that mapping to be configured and the immutable `oid` to be present; absence or ambiguity fails closed. Keep `sub` only as token/audience-specific metadata, never the cross-audience account key. The native-client-audience ID token used only as `POST /v1/devices` body proof is not an API bearer; the independently validated API access token remains mandatory. Resolve both tokens through the same pinned issuer/tenant + `oid` mapping (and matching `tid` where provided); their pairwise `sub` values may differ. Never use email/name, literal subject equality or client-authored mapping. Unconfigured immutable mapping blocks enrollment; missing/mismatched signed identity in a submitted token is rejected. Do not fetch token-supplied `jku` or accept a token merely because it decodes. Refresh/session material stays in Keychain; refresh is single-flight, failures require sign-in. If secure refresh rotation is supported by the configured policy, preserve the newest token atomically.

Revoked devices, deletion-pending accounts and removed entitlements are checked server-side on admission and during long streams. Device revocation takes effect immediately for new requests and within 5 seconds for active streams. Sign-out revokes the current device while online, closes streams, clears its Keychain session and disconnects local connector leases; offline sign-out clears local credentials immediately and warns that remote revocation could not yet be confirmed.

`DELETE /v1/account` requires recent verified authentication no older than 5 minutes plus `X-Pebbi-Reauth: required` and explicit typed confirmation. That header is not proof. The Entra deployment must supply a trustworthy authentication-time/step-up assertion in an API-verifiable token/policy; missing assertion fails closed with 403. Merely refreshing an access token or sending the local clock is not reauthentication. Configure and test this external identity requirement before enabling deletion.

## Request semantics beyond shape

### Bootstrap, plans and capability response

Device registration uses client-generated `installationId`, not hardware serials or persistent tracking identifiers. The public `deviceId`, installation ID and `enrollmentId` are not credentials. There are two bootstrap operations: `POST /v1/devices/enrollments` creates the OIDC nonce challenge; existing `POST /v1/devices` consumes it and returns `RegisterDeviceResponse.deviceToken` plus `deviceTokenConfirmBy` once. Both require the account API access-token bearer, but no device headers; registration also requires `X-Pebbi-Reauth: required` as an intent marker, never proof. No recovery, refresh or confirmation route is added.

**Standard OIDC challenge, not a custom assertion issuer.** `CreateEnrollmentRequest` contains exactly `schemaVersion: 1` and `installationId`. `CreateEnrollmentResponse` contains exactly `schemaVersion: 1`, `enrollmentId`, `authorizationNonce`, `expiresAt`. Generate a new UUID and 32 CSPRNG bytes, returning their canonical unpadded base64url encoding as `authorizationNonce`. Persist server-internal `EnrollmentChallengeRecord`: `enrollmentId`, bearer-resolved `accountId`, exact `installationId`, `authorizationNonceHash` (lowercase hex SHA-256 of the ASCII nonce string), `createdAt`, `expiresAt`, `consumed: false`. `createdAt` is server UTC time truncated to whole seconds; `expiresAt = createdAt + 300 seconds`. Never persist the raw nonce or accept client values for these server fields. The nonce has no device authority without fresh signed OIDC proof.

Native retains that challenge only in bounded attempt memory and starts ordinary Entra authorization-code + PKCE S256 with `scope=openid profile` plus configured API scopes (the Microsoft `oid` claim requires `profile`), a fresh local `state`, exact registered redirect URI, `nonce=authorizationNonce` and `prompt=login`. Request/enable the standard signed `auth_time` claim through the approved native-client registration/policy. Use `max_age` only if support and behavior have been verified for this exact deployment; it is not an assumed substitute for signed `auth_time`. Validate callback state and redirect locally, consume the callback once, redeem the code with the original verifier and validate the returned ID token locally before submission. State is a local CSRF/callback binding, not a backend proof field. Cancellation/expiry discards the attempt; no silent refresh or cached ID token replaces this login. The ordinary native-client-audience ID token is sent as `RegisterDeviceRequest.enrollmentIdToken` alongside `enrollmentId` and the same `installationId`, **only in the registration body, NEVER as generic API bearer authentication**. There is no special Entra purpose, assertion ID, enrollment-only audience, custom installation claim or enrollment JWT issuance API.

**Backend verification.** Independently validate the API access token and resolve the challenge under its account. Verify the ID token signature using approved algorithms and issuer-pinned keys, exact configured `iss`, native public-client `aud`, expected tenant/policy, valid `nbf`/`iat`/`exp`, and signed `nonce` whose hash matches the stored challenge in constant time. Reject token-supplied key/discovery URLs. Resolve the ID token to the same account as the API token using pinned issuer/tenant + verified immutable `oid` (and matching signed `tid` where provided), not literal `sub` equality; require request installation ID to equal the server-bound installation exactly. Require a signed numeric `auth_time`, no future authentication time, `now - auth_time <= 300 seconds`, `auth_time >= challenge.createdAt` and `auth_time > account.enrollmentNotBefore` where a threshold exists. `auth_time <= iat <= now < exp` must hold for this proof; its ordinary ID-token lifetime need not be five minutes because the challenge and authentication age independently enforce that window. At transaction commit require `now < challenge.expiresAt` without clock-skew extension. No `iat`, header, local clock, client JSON or newer bearer substitutes for signed authentication time. A one-second timestamp boundary may require another login; no freshness/threshold skew relaxation. Missing/invalid token proof, nonce or expired challenge is 403 `recentAuthenticationRequired`; missing/foreign-account challenge is 404 `notFound`; a known consumed own challenge is 409 `enrollmentConsumed`. Missing verified deployment support/mapping is 503 `enrollmentUnavailable` at either enrollment operation, never bearer-only enrollment.

**Bounded creation and replay.** At most one unexpired unconsumed challenge per account/installation and five per account; attempts exceeding an active limit get 429 `rateLimited`, with `Retry-After` until capacity can expire. Creating another challenge never invalidates an existing one. Hard ceilings are five creation attempts per account per rolling 300 seconds and twenty per source IP per rolling 300 seconds; completion attempts are capped at ten per account and thirty per source IP in the same window. Apply shared, atomic counters (stricter operator limits allowed), including invalid attempts after principal resolution; pre-auth IP limits also bound bearer-validation abuse. Challenge creation requires `Idempotency-Key`: store only canonical request digest, enrollment ID, outcome and times. A committed same-key replay is 409 `enrollmentConsumed`, not a replayed nonce; changed semantics are 409 `idempotencyConflict`; an in-flight duplicate is 409 `conflict`. If its 201 is lost, wait for that challenge to expire and create a new one with a new key. Failed proof checks do not consume a valid challenge or revoke a device; bounded counters prevent unlimited guesses. Unknown/expired/purged IDs never recreate state. Retain the minimal challenge row through `expiresAt + 60 seconds`, then delete it; the 60 seconds are cleanup/replay metadata retention, NOT an acceptance extension. Idempotency outcome/digest metadata lasts at most 24 hours and never includes raw nonce/ID-token/device-token bodies.

**Atomic lifecycle and revocation.** Serialize creation/completion/revocation/admission on the account security record. Before completion, enforce due pending-device expiry even if the worker is late, recheck deletion status, capacity, challenge account/installation/nonce/expiry and freshness against the current `enrollmentNotBefore`, then compare-and-set `consumed` once in the same transaction as device creation, credential digest, confirmation deadline and idempotency outcome. Concurrent use under another key cannot issue a second device. Initial threshold is absent (not client-selectable). Every first revocation advances `enrollmentNotBefore` monotonically to the server revocation time rounded upward to verified `auth_time` precision; proofs authenticated at/before it fail even for a different installation. Retain the threshold for the account lifetime and preserve it through backup restoration, independently of revoked-device cleanup. An enrollment committed before a later revoke is an existing device, not a replacement afterward; a later completion must satisfy the new threshold. Target-device revocation closes that target's authority, not every independently authenticated device. Consume no challenge if the transaction rolls back; a committed challenge never reopens, and expiry/cleanup can never make its old proof usable again.

Generate exactly 32 CSPRNG bytes and return their canonical unpadded base64url representation as `deviceToken`. Store only `SHA-256(decodedTokenBytes)` server-side, bound to account/device/installation/enrollment ID. Native stores the raw token in a non-synchronizing app/account/device-scoped Keychain item; never SQLite/UserDefaults. Compare digests in constant time after account/device lookup. Neither account bearer nor device token alone suffices. On every device-bound REST admission validate both, current revocation/confirmation status and account entitlement as applicable before replaying any cached result. Wrong/missing/foreign/revoked credential yields 403 `deviceCredentialInvalid` without revealing which check failed; malformed header shape is 400. Token lifetime after confirmation is until explicit device/account revocation; rotation requires fresh challenged enrollment and atomic retirement of the old credential, not an undocumented refresh endpoint. Do not describe this bearer credential as hardware-bound or protection against theft of both secrets.

**Single return and lost-response recovery.** A new device row is unconfirmed privately; `deviceTokenConfirmBy` is issuance + 300 seconds. The first successfully authenticated device-bound REST admission before that deadline atomically confirms possession (no confirmation route/body field); after confirmation the deadline does not expire the credential. Native saves the token before its first request. At the deadline an unconfirmed row is irreversibly revoked, advancing `enrollmentNotBefore` to that expiry time even if cleanup runs late. An unexpired unconfirmed installation cannot be registered again (409 `conflict`). If a registration 201 was lost or Keychain save failed, wait for pending retirement, create a new challenge, perform **new interactive authentication after retirement**, then submit the new proof and a new idempotency key. Do not authenticate early and wait out expiry. The replacement gets a new device ID/token; the uncertain predecessor stays revoked.

**Confirmed credential loss, including the last device.** No other working device is required forever. Native first offers unlocking an available Keychain item; loss/replacement requires an explicit accessible native review showing the account, exact same-installation device from `GET /v1/me`, and that its old credential and sessions will be revoked. Do not infer approval from a model, voice transcript or silent retry. The approved registration carries optional `replaceDeviceId` naming exactly that confirmed, nonrevoked account/installation record plus the new challenge/proof. The backend does not trust an approval boolean: fresh verified OIDC proof remains mandatory and the target binding is rechecked under the account lock. Without `replaceDeviceId`, an existing confirmed installation is 409 `conflict`; wrong/missing/foreign target is 404, and stale/revoked/unconfirmed target or installation mismatch is 409 with no changes. No cross-installation replacement or automatic choice of another device is permitted. After validating proof strictly against the **pre-transaction** threshold, atomically consume the challenge, revoke the exact old row, invalidate its pending session tokens, advance the threshold, and issue a new device ID/digest/confirmation deadline. Rollback keeps the old row unchanged and issues nothing. The replacement is authorized by that same atomic fresh-proof transaction; it cannot be required to authenticate after its own future commit time. Every subsequent enrollment must clear the newly advanced threshold, including any replayed replacement proof. Old streams close within 5 seconds. A concurrent revoke/another replacement forces revalidation and cannot revoke the new row or double-issue. A lost replacement 201 follows unconfirmed retirement recovery above, never reconstruction of either credential. Account bearer alone cannot replace, revoke through this path, or bypass review/fresh proof. If the Entra account itself is inaccessible, use the identity provider's recovery; Pebbi supplies no password/reset backdoor.

Registration's idempotency cache stores only canonical request digest, enrollment ID, outcome, resulting device ID and times, never `deviceToken`, `enrollmentIdToken`, raw nonce, an encrypted recoverable secret or response body. A committed same-key replay returns 409 `enrollmentConsumed`, not a reconstructed 201; concurrent in-flight duplicate returns 409 `conflict`. A transaction committed before a process crash is treated as possibly delivered, never regenerated. Expired idempotency cache does not resurrect a consumed challenge, revoked device or active installation. At most 50 retained device records remain enforced, including replacement predecessors; reject before consuming/revoking at capacity, never silently prune another record. Revoked records retain only security metadata for the retention window; a device ID is never reused. Raw proof/nonce material stays only in bounded native/gateway attempt memory and is excluded from body logging, caches, telemetry, exports, tool context and connectors.

First-party protocol references: [Microsoft ID-token claims (`aud`, `nonce`, pairwise `sub`)](https://learn.microsoft.com/en-us/entra/identity-platform/id-token-claims-reference), [Microsoft OIDC (`nonce`, `prompt=login`)](https://learn.microsoft.com/en-us/entra/identity-platform/v2-protocols-oidc), and [Microsoft optional claims (`auth_time`)](https://learn.microsoft.com/en-us/entra/identity-platform/optional-claims-reference). These document standard primitives; they do **not** verify this External ID tenant's `auth_time` issuance/precision, login freshness or cross-audience account mapping. Those remain [external-input gates](../operations/EXTERNAL-INPUTS.md).

A ready capability requires configured access and verified operation support; publish `verifiedAt` only for an actual successful role-specific probe, never a catalog fetch. A capability's model must match its role. Only ready, independently verified modes advertise usable formats/voice IDs. Transport limits and operator clamps are service safety budgets; only `tokenBudget.providerContextTokens` makes a deployment-verified provider-capacity claim. Readiness can change between discovery and dispatch; recheck at dispatch. Missing billing config returns `billingConfigured: false`, not a fake zero-cost subscription.

`Plans` lists Nest, Studio, Constellation. Each plan exposes the one configured purchasable interval/price in this contract; checkout rejects an unlisted interval. `price` and `allowance` are null until operator-approved. Amounts are integer minor units with uppercase ISO currency. `HostedBillingSession.expiresAt` uses provider evidence and may be null for a Portal link whose expiration is not returned; never fabricate it.

### Delivered token budgets

Every `RoleCapability` requires `tokenBudget`, either a complete `TokenBudget` or null. Its exact fields are `budgetId`, `providerContextTokens`, `maxInputTokens`, `maxOutputTokens`, `estimator`, `verifiedAt`, `expiresAt`. `TokenEstimator` contains `id`, `version`, `kind` (`verifiedTokenizer` or `conservativeBound`), `fixedOverheadTokens`, nullable `maxImageTokens`. Token units are integers. `providerContextTokens` is verified capacity for that deployment/operation, **not** an operator preference; `maxInputTokens`/`maxOutputTokens` are operator clamps with `maxInputTokens + maxOutputTokens <= providerContextTokens`. The existing 32,768 schema output ceiling is only an additional service limit.

A budget is all-or-null: missing capacity, estimator proof, clamps, or expired evidence yields null, not zero or a guessed default. Reasoning cannot be `ready` without a nonnull unexpired verified budget; use the canonical connection state and safe reason. Audio roles may have null token budgets only when their actual operation is independently bounded by verified audio-duration/message limits; null never authorizes native token-budgeted reasoning or screen input. `supportsScreenInput:true` requires nonnull deployment-verified `maxImageTokens`, a worst-case bound per accepted image across supported sizes/adapter tiling. If such evidence is absent, screen input remains disabled and full-product screen acceptance blocked.

The estimator identity/version must select a reviewed implementation available to both native and gateway, not remotely supplied executable code or a guessed characters-per-token rule. Count the full tool definitions, gateway-hidden instructions/wrappers (`fixedOverheadTokens`), visible instructions, history, user requests, attachment excerpts and image bounds. Tool-return expansion also needs headroom; billable tokens still come from trusted metering, not this estimate. If native lacks the advertised estimator implementation it must stop reasoning dispatch and request a compatible app update, never guess.

Define native usable input as `min(maxInputTokens, providerContextTokens - max(maxOutputTokens, ceil(providerContextTokens / 4)))`: this reserves at least 25% of verified capacity for output, future tool results and safety while honoring the operator input cap. `fixedOverheadTokens` and all current request components count within that usable input; it must remain positive after mandatory instructions. Begin compaction above 70% of usable input. Preserve instructions, pending approvals and cited evidence; if they cannot fit, request a narrower scope instead of dropping them. Reserved output must cover the requested output and all applicable limits; the gateway recomputes and enforces these constraints independently.

Capability evidence expires at most 24 hours after `verifiedAt`; refresh `/v1/capabilities` before a new task, after reconnect, before expiry and after any budget error. `budgetId` changes for any deployment, capacity, clamp, estimator, overhead or evidence revision. Native sends the exact ID in required `ResponseRequest.tokenBudgetId`; dispatch rechecks it against current authority. Mismatch is 409 `tokenBudgetChanged` before Azure dispatch; fetch the capability and recompute/compact with the new budget and an undispatched valid reservation or a new reservation if necessary. Never silently rewrite a stale client's ceiling.

If input is over budget, reject before dispatch with 400 `contextLimitExceeded`. An upstream context-limit failure uses `response.failed` with that same code once streaming started (or HTTP 400 before SSE headers); do not report `length`/success. Invalidate the offending budget immediately, publish null/nonready until a smaller justified budget is verified, then deliver a new ID. Never lower the claimed provider capacity solely from a guessed tokenizer correction: repair measured estimator/overhead or clamp, and reverify capacity as needed. Allow at most one explicit shrink-and-retry with a new inference request/reservation after a valid replacement budget; retain original evidence/intent locally and disclose any narrowing. No automatic generation retry after uncertain chargeable dispatch.

### Inference and tools

`ResponseRequest` includes `taskId`, `attemptId`, `pebbiId`, a unique `requestId`, reservation, `afterSequence`, current `tokenBudgetId`, bounded messages, tool definitions and an operator-clamped output ceiling. The reservation owner/account/device/task/attempt/role must all match. Client `pebbiId` and task IDs correlate local work, not an assertion of server-persisted Pebbis.

`input` accepts text, selected images, prior tool proposals and sanitized tool-result content only. The `user` role may carry text/images; `assistant` carries prior text and `toolProposal` blocks (`callId`, canonical `tool`, untrusted `arguments`); `tool` carries only `toolResult` blocks with a matching preceding proposal `callId`. Stateless continuation replays these bounded history blocks; it does not rely on a hidden server conversation or invented provider previous-response endpoint. The adapter preserves or translates opaque provider call references through the gateway correlation mapping. Reject role/content mismatches or unknown tool results. Client-provided history is untrusted context, not policy. Gateway-controlled system instructions cannot be overwritten by client roles.

The local registry validates `ToolDefinition.inputSchema` as bounded JSON Schema 2020-12, with no remote `$ref`, code-evaluating keywords or unbounded recursion. Backend validates shape and size but does not execute tools. `response.tool.proposed` is an untrusted proposal with complete parsed arguments, not a partially streamed executable object. Map gateway `tool` to native `toolName` and gateway `callId` to the opaque `providerCallRef` correlation in a `ToolProposal`; the broker creates a separate local UUID `toolCallId`. Keep this mapping for the next `ContextToolResult.callId`; never confuse Azure/provider tokens with local IDs. Only canonical local tool names from TOOLS.md are exposed, including `stageTextArtifact` alongside the existing names; dynamic MCP tools are wrapped by `callConnectionTool`. `stageTextArtifact` explicitly stages bounded model-authored UTF-8 chunks in the native broker and returns real immutable artifact IDs/hash before create/replace/run; ordinary assistant prose is never implicitly a file or executable. Its closed per-tool schema, scope, retries and private-mode behavior belong to TOOLS.md and the tool-envelope schema; the gateway name enum is not permission to execute. Native broker produces an immutable validated [tool envelope](schemas/tool-envelope.schema.json), performs permission/approval/capability checks, and supplies the verified result in the next inference call with a new reservation. Never continue automatically after rejected/unknown effects.

### Errors

Nonstreaming error body is always `Error`: `schemaVersion`, `error.code`, safe `message`, `requestId`, `retryable`, nullable `retryAfterSeconds`. The schema enumerates every code. No raw Azure/Stripe/MCP error body, path, key or prompt leaks through it. Internal audit may retain the allowlisted provider error code without payload.

| HTTP | Typical codes / client behavior |
| --- | --- |
| 400 | `invalidRequest`, `contextLimitExceeded`; correct input/refresh verified budget, no blind retry loop. |
| 401 | `unauthenticated`; one synchronized refresh if applicable, otherwise sign-in. Include `WWW-Authenticate`. |
| 403 | `forbidden`, `approvalRequired`, `untrustedMetering`, `accountDeleting`, `deviceCredentialInvalid`, `recentAuthenticationRequired`; do not bypass. Invalid device credential does not trigger a bearer refresh loop. |
| 404 | `notFound`; missing and foreign-owned resources are indistinguishable. |
| 409 | `conflict`, `idempotencyConflict`, `reservationExpired`, `enrollmentConsumed`, `tokenBudgetChanged`; inspect the affected lifecycle; never regenerate a secret or duplicate work. |
| 413 / 415 | `payloadTooLarge` / `unsupportedMediaType`; reduce/correct selected input before retry. |
| 429 | `quotaExceeded` or `rateLimited`; distinguish subscription allowance from request-rate throttling. Honor `Retry-After`. |
| 500 | `internalError`; do not expose exception stacks. |
| 502 | `providerUnavailable`; upstream response was malformed/unusable. |
| 503 | `capabilityUnavailable`, `providerUnavailable`, `billingNotConfigured`, `exportNotReady`, `enrollmentUnavailable`; explain unavailable dependency; honor `Retry-After` when present. |
| 504 | `providerTimeout`; outcome may be uncertain; reconcile before dispatch retry. |

`streamInterrupted` is a streaming/disconnection error code and not a claim that a task failed safely. No undocumented HTTP 402 is used. Schema-validation failures occur before chargeable dispatch; started upstream work may still consume usage if its response fails or the user cancels.

## Idempotency and race rules

- Required on enrollment-challenge creation, device mutations, reservations/finalization, Checkout/Portal, export and account deletion. Scope keys by account/service principal + method + exact path; hash canonical validated request bytes, including relevant path parameters, not volatile tracing headers. Reuse with different semantics returns 409 `idempotencyConflict`.
- Persist pending/committed/failed dispatch metadata before an external side effect. Concurrent same-key requests wait a bounded time or return 409 while in flight, never double-dispatch. Successful results are retained 24 hours **except enrollment-challenge creation, registration and audio tokens, whose nonce/secret-bearing bodies are never retained/replayed**; webhook IDs and metering uniqueness follow the longer billing policy. Authenticate account and device credential before every device-bound replay; a newly revoked caller cannot replay a cached 204 or export URL.
- Replays of export intentionally return the same `exportId` with its **current** `exportState`; pending has null URL/expiry, ready has a signed URL/expiry, failed has null URL/expiry. This is observation of one job, not a second job. Poll same POST/key/body at most once every 2 seconds, exponential backoff capped at 30 seconds. The 202 response remains the same resource contract when ready. URLs expire after 15 minutes; a same-key authenticated observation may issue a new URL for the same artifact during its 24-hour lifetime. No status route is invented.
- SSE generation is not replayable. Unique `ResponseRequest.requestId` + reservation must be atomically claimed once. Reusing an already dispatched request returns 409, not a fresh generation or reconstructed stream. Keep only metadata/hash for 24 hours, never prompt/output content for replay. HTTP reconnect/resend must not charge twice behind the user's back.
- Audio token creation is deliberately not replayable: a reservation supports one pending/active session. A lost 201 response is recovered by letting its unused 60-second token expire and requesting a new reservation/session; repeated creation against the old reservation is 409. Never return the same bearer secret from an idempotency cache.
- Finalization is one charge per provider operation/reservation. End-user API calls cannot finalize, release or claim zero usage. Worker retries use the same key/evidence; conflicting values go to reconciliation, not ledger overwrite.

## SSE protocol

`POST /v1/ai/responses` uses `Accept: text/event-stream`. Validate authentication, schema, provider capability and reservation before committing HTTP 200. Until then return a normal JSON error. Once streaming starts use `Content-Type: text/event-stream; charset=utf-8`, `Cache-Control: no-store`, disabled proxy buffering/compression that delays frames, and flush each bounded frame.

Each event is framed as:

```text
id: <eventId UUID>
event: <type>
data: <one JSON object conforming to ResponseEvent>

```

There is no vendor `[DONE]` sentinel. `schemaVersion`, `eventId`, `taskId`, monotonic task-local `sequence`, `type`, UTC `occurredAt`, and `payload` are present. Send `: keepalive` comments every 15 seconds while waiting. Maximum decoded event size is 64 KiB. Bound unsent data to 256 KiB or 5 seconds, then cancel a persistently slow consumer. Engineering timeouts: first upstream output within 30 seconds, total reasoning call 300 seconds; actual supported ingress budgets must be tested and aligned.

Ordering for one call:

1. `response.started` supplies generated `responseId` and locked Astra model.
2. Zero or more `response.text.delta` and/or complete `response.tool.proposed` events.
3. Exactly one of `response.completed`, `response.cancelled`, `response.failed`, then close. Completion `usage` contains verified server quantities, or null when metering still needs reconciliation; never fabricate zero usage. `/v1/usage` remains the accounting authority. `finishReason: toolProposals` means native work is pending, not task success. `length` means truncated model output, not permission to claim completion.

The backend allocates a monotonically increasing **transport** sequence per account/device/logical task across its provider streams; `afterSequence` is the client's durable remote cursor. Start above both accepted cursor and server high-water mark, checked against the safe integer bound. Only one active reasoning provider stream per agent-task owner is admitted. Audio uses independent operation owners as defined below, not that task slot. Counter metadata is not conversation sync. The native Store assigns its own journal sequence while preserving remote `eventId` and `sequence` as source metadata; do not interleave transport numbers into local journal primary keys. Deduplicate remote event IDs and reject regressions. An attempted new stream cannot reset the high-water mark. Cross-task ordering is not defined.

No server event replay is available: `Last-Event-ID` must not trigger provider execution or invented backfill. Closing the HTTP stream propagates abort to Azure and releases unused reservation capacity after server metering reconciliation. A user task cancel separately advances native `cancelling` → `cancelled` only after owned resources stop; the native runtime cancels all its associated transports and pending tool dispatch. The transport cannot acknowledge its own disconnect, so absent terminal event means uncertain/interrupted work, not success. Already-sent effects require target read-back before retry. A 200 alone is never model/task completion.

## WebSocket protocol

These are **Pebbi gateway protocols**, not claims about Azure wire names. Complete message schemas are `AudioClientMessage` and `AudioServerMessage` in OpenAPI; `x-websocket` associates them with the exact upgrades.

### Admission and token lifecycle

1. Create native audio ownership and reserve usage for `conversation` or `dictation`; wire `taskId`/`attemptId` carry `audioOperationId`/`audioAttemptId`. Request the corresponding session with the same audio owner/attempt/reservation, not a queued task ID. Choose a voice/audio format only from the actually verified capability. No freeform upstream endpoint, model, codec or token is accepted.
2. Server verifies account bearer **and** matching device ID/credential, scopes, role readiness, limits and immutable reservation ownership. It creates a CSPRNG token with at least 256 bits entropy; returns token once plus `sessionId`, same-origin relative `streamPath`, `expiresAt` (60 seconds), `subprotocol: pebbi.audio.v1`, accepted format and 600-second session maximum. Store a token digest with account/device/audio operation/audio attempt/reservation/role/path binding, not the raw token. Do not cache/log the response.
3. Native URLSession opens `wss` on that origin and exact path with `Authorization: Bearer <sessionToken>`, `X-Pebbi-Device-Id`, `Sec-WebSocket-Protocol: pebbi.audio.v1` and the normal RFC 6455 upgrade headers. No app bearer or Azure key is sent as the session token; `X-Pebbi-Device-Token` is forbidden on upgrades. Session minting already checked the device credential and the session token independently binds that device/role. Reject query credentials, missing/wrong subprotocol, wrong role/path/device, expired/reused token and unapproved browser Origin. Native no-Origin is allowed only for the authenticated native protocol. Tokens are not conveyed in the subprotocol.
4. Atomically consume token and claim reservation before HTTP 101. Replay/concurrent upgrades lose. Failed upgrades after consumption require a new session; never relax one-use semantics. Before 101 use the normal JSON errors. An unused expired token releases its hold if there is no dispatched provider work.
5. The upgrade token's 60-second lifetime is **admission only**, not a requirement to disconnect a healthy stream after 60 seconds. Active authority is the server-side session and account/device/entitlement checks; absolute session limit is 600 seconds, plus ceiling and revocation. Never renew authority via a model message.

### Message and frame rules

Use UTF-8 JSON text **messages**, possibly fragmented into RFC 6455 text/continuation frames; binary messages are rejected with 1003. Disable WebSocket compression (`permessage-deflate`) to avoid an extra unbounded inflate layer. This deliberately avoids a second custom binary protocol. Audio is base64 PCM signed 16-bit little-endian, mono, at the negotiated sample rate (only verified 16000/24000/48000 Hz may be advertised). Server may adapt/resample only to a verified upstream format and must account from actual accepted samples. Do not claim a provider natively accepts all client formats.

Each reassembled serialized JSON text/control/transcript/context **message** is at most 256 KiB UTF-8 bytes including envelope, whitespace and escaping. `audio.append` and `voice.output.audio` retain a tighter 32 KiB serialized-message cap plus at most 16 KiB decoded PCM and an even PCM byte count. Independently, every data-frame payload is at most 32 KiB; fragment larger text messages, bounding cumulative reassembly before allocation/JSON parsing. Control frames obey RFC 6455's 125-byte limit and cannot fragment. The advertised `maxFrameBytes`, `maxMessageBytes`, `maxAudioMessageBytes`, `maxDecodedAudioBytes` distinguish these limits. Schema `maxLength` is Unicode code points, never a byte limit. Encoders emit non-ASCII directly, escape JSON-required characters and avoid splitting code points; receivers incrementally validate UTF-8 across continuation boundaries (a code point split by a conforming peer is reconstructed, not corrupted). Reject invalid UTF-8/lone surrogate values; fragmentation never resets the byte counter. Enforce audio message size after identifying its type as well as the generic preparse cap. Audio chunks represent 20–100 ms each; enforce duration from bytes/rate, not a client timestamp. `clientSequence` starts at 1 and increments exactly once per client JSON message; `clientEventId` is a UUID. `audio.append` carries `utteranceId` on every input chunk, so partial transcripts before commit have an unambiguous owner. The same `utteranceId` must appear in `audio.commit`. `chunkIndex` starts at 0 and increments over the session's input chunks; output chunk indices restart per `outputId`. Gaps, conflicting duplicates, invalid IDs, wrong session IDs, out-of-state commands or malformed PCM fail closed. A same-event duplicate with identical content can be acknowledged without reconsumption; never bill a duplicate twice. No buffered audio is replayed on reconnection.

Server envelopes use an **audio-operation-local** transport cursor, independent of SSE agent-task cursors; wire `taskId` is the audio operation alias, and payloads carry `sessionId`. Native deduplicates into `audio_event_receipts`, never agent-task foreign keys. At most one uncommitted utterance is buffered per session and at most 1 second of unacknowledged audio can be in flight. `audio.accepted` acknowledges the highest accepted client sequence, not paid usage authorization. Backpressure pauses capture; do not silently accumulate recordings. An unacknowledged buffer exceeding 5 seconds causes a retryable failure and clearing of volatile audio. Send WebSocket ping every 20 seconds; require pong within 10 seconds. Dead connections abort provider work and reconcile usage.

### Audio ownership and concurrent task handoff

Native `audio_operations`/`audio_event_receipts` own audio IDs, account/device/Pebbi/conversation references, immutable role/reservation, volatile session handle, transport cursor and lifecycle, independent of the serial task queue. Reservation/session wire `taskId` means `audioOperationId`, `attemptId` means `audioAttemptId`; SSE reasoning retains actual agent task/attempt IDs. Server infers owner kind from immutable reservation role (reasoning versus conversation/dictation), binds the session to it and rejects owner UUID reuse across incompatible roles with 409 `conflict`. There is no new event field or task-state enum. Server events need not add attemptId: the authenticated session/reservation resolves the audio attempt.

A voice session may open with no queued task. When the user requests work, create a **distinct real agent task/attempt** and reasoning reservation. Astra runs while the audio operation stays available; one provider stream per owner remains enforced, with separate account audio/reasoning quotas. Native serializes actual agent attempts per Pebbi, not audio ownership. On verified task completion, route `conversation.context` to the still-authorized audio session: `sourceTaskId`/`sourceAttemptId` identify the real agent result and never replace audio owner IDs. Wait for listening/no pending utterance/output before submitting context. Stop/interrupt the audio output/session without cancelling or changing that task.

Standalone dictation likewise allocates independent audio ownership while a Pebbi's task is running or waiting. One device microphone lease prevents competing voice/dictation input capture; explicit user choice may pause/replace voice capture with dictation, close/reconcile the old audio operation as appropriate, and leave the agent task unchanged. Audio crash recovery closes/interrupts audio ownership and reconciles reservations without enqueuing a task retry. No audio is automatically replayed, including after capture handoff or transport recovery.

### Conversation sequence

```text
POST /v1/usage/reservations             role=conversation
POST /v1/voice/sessions                approved format + voice
GET /v1/voice/stream -> HTTP 101        one-use token, correct headers
client session.start                  empty payload; clientSequence=1
server session.ready                  accepted role/format
server voice.state                    listening
client audio.append ...               bounded chunks, acknowledgements
client audio.commit                   utteranceId; freezes this utterance
server voice.input.transcript         provisional/final text if verified upstream supports it
server voice.state                    thinking, then speaking
server voice.output.audio/text ...    outputId + ordered playable chunks/text
server voice.output.done              interrupted=false
server voice.state                    listening
client session.stop                   stop after committed work drains, bounded 5 seconds
server session.closed                 reason=completed; WebSocket 1000
```

`session.start` must arrive within 5 seconds; otherwise close 1008. `audio.commit` ends the utterance and requests the upstream response using its verified protocol. Do not invent a transcript when the provider supplies only audio; lack of verified transcript support cannot masquerade as a final transcript for task execution. Voice intent requiring tools is handed to the native task coordinator and Astra; streamed audio never runs tools directly.

For barge-in, the client stops playback immediately and sends `response.interrupt {outputId}`. Server cancels/truncates only that audio response using supported upstream behavior, drops future chunks for it, emits `voice.output.done {interrupted:true}` and `voice.state: interrupted`, then returns to `listening`. If upstream truncation is unavailable, stop that upstream response/session honestly rather than pretend interruption synchronized history. This does **not** cancel an associated agent task. Late audio cannot resume playback after the output ID is cancelled. `response.interrupt` is rejected on dictation sessions.

### Pebbi context and speaking verified task results

`VoiceSessionRequest.contextSummary` carries only the selected Pebbi/job/memory/conversation summary (maximum 16,000 characters; empty allowed), not system policy or credentials. Gateway-owned safety instructions remain separate. A ready full-product conversation capability requires independently verified `supportsContextInput`; missing text/context input support is a capability gate, never a claimed workaround through another model.

While the conversation is `listening` with no uncommitted utterance or output, the native app may send `conversation.context` with a strictly increasing session-local `revision`, bounded `text`, nullable `sourceTaskId`/`sourceAttemptId`, and `speak`. The server acknowledges `conversation.context.accepted` after the verified upstream operation accepts it. Context changes affect only subsequent responses and never mutate an in-flight utterance. `speak:false` refreshes selected context without unsolicited speech. `speak:true` requires the native coordinator's verified task/attempt result references and asks the selected conversation model to speak that result; normal `voice.state` and output events follow. The backend checks shape/session capability, while native trusted records establish actual tool verification. A caller's text alone is not proof a task succeeded.

Screen images stay on the Astra reasoning path. Its verified explanation/result can be supplied through this context message for speech; do not send unrelated raw screenshots to the conversation session or install a substitute TTS model. Typed tasks likewise use Astra; speaking a result does not repeat its tools or change task state. `conversation.context` is rejected for dictation and when its capability is unavailable. No context transcript is retained server-side after session end.

### Dictation sequence

```text
POST /v1/usage/reservations             role=dictation
POST /v1/dictation/sessions             format + nullable languageHint
GET /v1/dictation/stream -> HTTP 101    one-use token
client session.start
server session.ready
native state capturing
client audio.append ...
server dictation.state                 transcribing when provider starts
server dictation.transcript.partial    replacement draft, never inserted
client audio.commit                   utteranceId
server dictation.transcript.final     entire final utterance text
client session.stop
server session.closed                 reason=completed; WebSocket 1000
native reviewing -> inserting -> completed, only after current focus check
```

Use one utterance per dictation session. Partial text replaces the current draft rather than appending duplicate hypotheses; only a full final transcript closes the utterance. The 32,000-code-point final/16,000-code-point context ceilings remain in the schema but must also pass the message-byte limit. On a character or encoded-byte overflow, never truncate and emit final: fail explicitly with `payloadTooLarge`, preserve already delivered local review text as incomplete, and require a shorter/new utterance. The gateway cannot promise recovery of never-delivered provider text and must not invent a success or store a server transcript. Backend never emits `inserting` or local `completed` as evidence that another app changed. Those transitions and exact-target verification belong to the Mac. A no-final close is a failure, not an empty successful transcription. Dictation `capturing`, `reviewing`, `inserting` and `completed` are local UI states; server `dictation.state` is limited to `transcribing` or `failed` despite sharing the canonical enum.

### Stop, cancel, close and recovery

`session.stop` stops accepting new input; it drains only already committed work for at most 5 seconds, never commits an uncommitted utterance implicitly. Discard uncommitted audio. A dictation final not received before drain timeout is failed, not complete. `session.cancel` immediately stops recording/playback/transcription and clears volatile buffers; reason `taskCancelled` is sent only for an explicit real task cancellation whose native routing deliberately closes associated audio; audio owner IDs are never interpreted as task cancellation requests. `session.cancel` does not claim externally executed tools were undone. Sleep, quit, device change or account revocation stops capture and closes authority; no hidden audio reconnection or microphone restart after Quit.

Server sends `session.error` with a sanitized `Error`, then `session.closed` when transport permits. Close codes: 1000 normal completion/cancel; 1008 protocol/authorization/session-expiry violation; 1009 oversized frame or reassembled message; 1007 invalid UTF-8; 1011 provider/internal failure; 1012 controlled service restart; 1013 temporary overload/quota. Close reasons are short safe codes, no content. Quota exhaustion or provider disconnect preserves local review text, rejects new work and reconciles consumed usage. Native state becomes canonical `unavailable`/`failed` for voice or `failed` for dictation; never a synthetic success.

Reconnect creates a new reservation/session/token after the old session has stopped/reconciled or expired. It does not resume audio, repeat committed utterances, resurrect an attempt or replay tools. The user can explicitly retry with a new audioAttemptId linked to the audio operation after old ownership is terminal; a different role uses a new audio operation. This is not an agent-task retry. Transport success and useful audio/transcription success are independently tested.

## Export, deletion and privacy

`POST /v1/account/export` includes server-held account, devices, entitlement and usage information only. It excludes provider secrets, connector tokens, other users' data and raw local conversations/files/screens. The native app combines that artifact with a separately consented local export; `includesLocalData` remains false for the server result. Download URLs are read-only, object-scoped, short-lived and never logged. Pending/failed/ready schema combinations are validated semantically.

`DELETE /v1/account` atomically marks deletion pending, revokes device/session admission, blocks new billing/model work, and enqueues subscription cancellation and deletion. Return server deadlines: active eligible data within 30 days, backup expiry no later than 35 days after active deletion. Legal billing-retention exceptions are disclosed before confirmation; raw model content was never retained as account history. Current-device local erasure is separately verified by the app; other offline Macs and user-created exports cannot be remotely erased by this contract. See [SECURITY](SECURITY.md) and [BILLING](BILLING.md).

### Repair-specific rejection and race cases

These are required implementation tests; static schema fixtures alone cannot prove them:

- **H01:** Valid account bearer plus another owned device ID and no matching device secret is 403 `deviceCredentialInvalid`; token A + ID B and token without account bearer also fail. Normal bearer/ID token, locally asserted authentication time, wrong issuer/audience/purpose/installation/account, silent refresh and stale interactive evidence do not enroll. Revocation followed by old assertion replay (even new installation/key) is rejected. Exercise concurrent revoke/enroll, same-key/changed-key assertion replay, lost 201, crash after commit, Keychain failure, pending expiry and late reaper; a fresh assertion obtained **before** pending retirement cannot create its replacement. Verify digest-only storage, single response delivery, cache/log/export redaction and restored thresholds. These need actual identity-policy and DB/Keychain tests, not fabricated JWT success.
- **M01:** Schema-valid 11,000 CJK characters in final transcript/context are admitted within the new message cap and fragmented as needed. Cover maximum ASCII, CJK, emoji and escape-heavy/control text; exactly-at-limit and over-limit serialized byte counts, oversized individual frames, cumulative fragmented overflow, multibyte continuation boundaries, invalid UTF-8/lone surrogates, decoded PCM over 16 KiB, odd PCM and 32 KiB audio-message overflow. A schema-valid string can still fail the byte-budget validator. Never silently truncate final text or report a partial as complete.
- **M03:** Missing `tokenBudget`, null ready-reasoning budget, incomplete budget/estimator, unknown estimator version, expired evidence, impossible input/output sums, missing image bound and stale `tokenBudgetId` fail at the applicable schema or semantic boundary. Recheck changed deployment/clamps at dispatch; context-limit failure invalidates budget and preserves instructions/evidence for explicit recovery. Token counts are estimates until trusted metering.
- **H03 / tools:** Voice with no agent task → request real work → independent Astra reservation while voice remains open → speak the verified result via real task provenance → interrupt/stop audio without task cancellation. Standalone dictation while that Pebbi's task waits uses a separate audio owner and explicit microphone handoff. Cross-role owner reuse fails; audio receipts never enter task FKs. `stageTextArtifact` is accepted by both canonical name enums; native closed-schema/chunk-replay/scope/privacy tests and generated-file/script creation from an empty workspace are required by TOOLS/quality, not certified by the gateway enum.
